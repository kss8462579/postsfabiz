설비 데이터 수집: OPC UA와 MQTT 중 무엇을 쓸까

OPC UA와 MQTT는 역할이 다르다. 구간별 선택 기준과 각각에서 자주 만나는 장애, 점검 순서를 정리한다.

이 포스팅은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

"OPC UA를 쓸까, MQTT를 쓸까"라는 질문은 둘을 같은 종류로 놓고 시작한다. 실제로는 푸는 문제가 다르다. OPC UA는 "이 데이터가 무엇이고 제어기에서 어떻게 읽는가"에 답하고, MQTT는 "여러 송신자의 메시지를 여러 수신자에게, 내가 다 통제하지 못하는 네트워크로 어떻게 보내는가"에 답한다. 수집 프로젝트가 꼬이는 경우는 대개 한쪽에 다른 쪽의 일을 시켰을 때다.

두 프로토콜이 주는 것

OPC UA(IEC 62541)는 기본적으로 클라이언트/서버 방식이다. PLC에 내장되거나 옆의 게이트웨이에서 도는 서버가 주소 공간을 공개한다. 주소 공간은 데이터 타입과 구조를 가진 노드의 트리이고, 클라이언트가 탐색할 수 있다. 클라이언트는 세션을 열고 노드를 읽거나 구독을 만든다. 구독에서는 서버가 요청받은 샘플링 주기로 값을 보고, 변화가 있으면 퍼블리싱 주기에 맞춰 보낸다. 보안은 규격에 포함되어 있다. 애플리케이션은 인증서로 서로를 확인하고 메시지는 서명 또는 서명과 암호화를 적용할 수 있다.

MQTT(OASIS 표준)는 브로커를 중심으로 한 발행/구독 전송 방식이다. 클라이언트가 plant/line3/press2/temperature 같은 토픽에 데이터를 발행하면 브로커가 그 토픽을 구독한 모든 클라이언트에 전달한다. 발행자와 구독자는 서로 직접 연결하지 않는다. QoS 세 단계, 리테인 메시지(토픽의 마지막 값을 브로커가 보관), 유언 메시지(클라이언트가 비정상 종료되면 브로커가 대신 발행)를 규격으로 정한다. 페이로드 안에 무엇을 어떤 형식으로 넣을지는 정하지 않는다. 그 부분은 전부 사용자 몫이다.

항목 OPC UA (클라이언트/서버) MQTT
연결 구조 클라이언트가 서버마다 접속 모두가 브로커로 접속
데이터 의미 타입과 구조가 정의됨, 탐색 가능 정의 없음, 자체 규칙 필요
접속 방향 장비 쪽으로 들어옴 장비에서 밖으로 나감
수신처 추가 서버마다 세션 추가 브로커에 구독 하나 추가
설비로 쓰기 기본 제공(쓰기, 메서드 호출) 가능하지만 직접 설계
주로 쓰는 구간 제어기 ~ 게이트웨이/SCADA 게이트웨이 ~ MES, 저장소, 클라우드

프로젝트가 아니라 구간별로 고른다

제어기에서 엣지까지. PLC에 OPC UA 서버가 있으면 그것을 쓴다. 레지스터 주소표를 손으로 관리하지 않아도 제어기 프로젝트의 이름과 타입이 그대로 넘어오고, 노드 단위로 접근을 제한할 수 있다. 서버가 없는 구형 제어기는 제조사 전용 드라이버나 필드버스 게이트웨이로 읽고, 게이트웨이가 OPC UA로 공개하거나 MQTT로 발행하게 한다.

엣지에서 상위 시스템이나 클라우드까지. 수신처가 여럿이거나, 회선이 불안정하거나, 수신 측이 다른 네트워크 구역에 있으면 MQTT가 맞다. 장비는 브로커로 나가는 연결만 있으면 되므로, 설비마다 들어오는 포트를 여는 것보다 방화벽 검토가 훨씬 수월하다.

작고 단순한 구성. 설비 몇 대와 수집 서버 하나가 같은 네트워크에 있다면 브로커는 관리할 대상만 늘린다. OPC UA 직접 접속으로 충분하다.

두 기술은 겹치는 부분도 있다. OPC UA 규격에는 MQTT 브로커를 전송 수단으로 쓸 수 있는 PubSub 모델이 있고, Sparkplug 규격은 MQTT 위에 토픽 구조와 페이로드 형식, 장치 상태 관리를 정해 둔다. 둘 다 MQTT가 데이터의 의미를 정하지 않기 때문에 나온 것이다. 지원 여부는 제품마다 다르므로 설계 전에 제어기와 소프트웨어가 실제로 무엇을 지원하는지 확인한다.

OPC UA 쪽에서 만나는 장애

네트워크는 정상인데 접속이 안 된다. 가장 흔한 원인은 인증서 신뢰다. 양쪽이 서로의 인증서를 신뢰해야 하고, 많은 서버가 처음 보는 클라이언트 인증서를 거부 목록에 넣어 둔다. 이것을 신뢰 목록으로 옮겨야 한다. 방화벽보다 이것을 먼저 본다. 그다음은 클라이언트가 요청한 보안 정책과 서버가 허용한 정책의 불일치, 엔드포인트 주소의 호스트 이름을 클라이언트가 해석하지 못하는 경우, 시계가 크게 어긋나 인증서 유효기간이 맞지 않는 경우 순이다.

짧은 신호가 데이터에 없다. 구독은 서버가 샘플링 주기에 본 값만 알려준다. 두 샘플 사이에 켜졌다 꺼진 비트는 나타나지 않는다. 주기를 줄여 달라고 요청해도 서버가 지원하는 한도까지만 적용되고, 내장 서버는 요청보다 느린 값으로 조정해 응답하는 경우가 많다. 펄스나 횟수는 PLC에서 래치하거나 카운트한 뒤 그 값을 수집한다.

서버가 느려지거나 새 세션을 거부한다. 내장 서버는 세션, 구독, 감시 항목 수에 한도가 있고 제어 프로그램과 CPU를 나눠 쓴다. 한도는 모델과 펌웨어에 따라 다르므로 매뉴얼에서 확인한다. 여러 클라이언트가 같은 태그 수천 개를 각자 구독하는 것이 한도에 걸리는 전형적인 경로다. 수집기 하나가 읽어서 나눠 주는 구조로 바꾼다.

값이 멈춘 것처럼 보인다. 데드밴드가 너무 넓거나, 네트워크가 끊긴 뒤 구독이 사라졌는데 클라이언트가 다시 만들지 않은 경우다. 해당 노드를 직접 읽어 비교하면 구분된다.

MQTT 쪽에서 만나는 장애

수신처마다 데이터를 다르게 해석한다. 토픽 체계와 페이로드 형식을 정하지 않으면 발행자마다 제각각이 된다. 첫 장비를 붙이기 전에 토픽 단계(사업장/구역/라인/설비/신호), 페이로드 형식, 단위를 정하고, 시각은 수신 측이 아니라 발생 지점에서 찍는다.

중복되거나 빠진다. QoS 0은 유실될 수 있다. QoS 1은 최소 한 번 전달을 보장하므로 재접속 뒤 중복이 생길 수 있다. 수신 측에서 발생 시각과 태그를 키로 삼아 중복을 걸러낸다. QoS는 클라이언트와 브로커 사이 구간별로 적용되며, 발행 장치가 오프라인인 동안의 데이터는 장치가 자체 버퍼링을 하지 않으면 보호되지 않는다.

멈춘 설비가 정상 값으로 보인다. 리테인 메시지는 브로커에 계속 남는다. 장치가 죽어도 새 구독자는 마지막 값을 현재 값처럼 받는다. 유언 메시지로 오프라인 상태를 명시적으로 발행하고, 모든 값에 시각을 붙여 오래된 데이터를 알아볼 수 있게 한다.

한꺼번에 다 멈춘다. 브로커는 구조상 단일 장애점이다. 엣지의 로컬 버퍼링, 브로커 자체 감시, 필요하면 이중화를 계획에 넣는다.

보안과 쓰기 권한

OPC UA는 보안 정책 "None"과 익명 접속을 운영 환경에 남겨 두지 않는다. MQTT는 TLS, 클라이언트별 계정, 토픽 접근 규칙을 브로커에 설정한다. 인증 없는 브로커에서는 네트워크의 어떤 장치든 아무 토픽에나 발행할 수 있다.

읽기와 쓰기 경로는 따로 다룬다. 수집에는 읽기 권한만 있으면 된다. 상위 시스템이 레시피나 설정값을 내려야 한다면 특정 노드나 토픽으로 한정하고, PLC가 범위와 설비 상태를 검증한 뒤 받아들이게 한다. 동작 기동과 안전 관련 파라미터는 원격 데이터 경로가 아니라 설비 자체의 제어와 안전 기능 아래에 둔다.

확정 전 점검 순서

  1. 데이터 수신처를 나열한다. 하나면 OPC UA만으로 충분하고, 여럿이거나 다른 구역에 있으면 상위에 브로커를 둔다.
  2. 제어기별 기본 지원 프로토콜과 세션, 항목 수 한도를 매뉴얼에서 확인한다.
  3. 이름 규칙을 정한다. PLC의 노드 구조와 브로커의 토픽 체계가 일대일로 대응해야 한다.
  4. 시각 기록과 버퍼링 위치를 정한다. 둘 다 설비에 가까울수록 좋다.
  5. 장애 상황을 벤치에서 시험한다. 랜선을 뽑고, 브로커를 재시작하고, PLC를 재시작한 뒤 수신 측에 무엇이 보이는지, 수동 조치 없이 복구되는지 확인한다.

다섯 번째 단계가 가장 자주 생략되는데, 두 프로토콜의 차이가 가장 분명히 드러나는 곳이 여기다.
