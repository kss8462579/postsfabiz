OPC UA vs MQTT for shop-floor data collection: which to use where

OPC UA and MQTT solve different halves of the data collection problem. How to choose per layer, and the faults each one produces.

The question usually arrives as "should we use OPC UA or MQTT?", but the two were built to answer different questions. OPC UA answers "what is this data and how do I read it from a controller?". MQTT answers "how do I move messages from many senders to many receivers over a network I do not fully control?". Most collection projects that run into trouble picked one of them to do the other's job.

What each protocol actually gives you

OPC UA (standardised as IEC 62541) is, in its classic form, a client/server protocol. The server, often built into the PLC or running on a gateway next to it, exposes an address space: a browsable tree of nodes with data types, engineering units and structure. A client opens a session, browses or addresses nodes, and either reads them or creates a subscription. In a subscription the server samples each monitored item at a requested sampling interval and sends changes at a publishing interval. Security is part of the specification: applications identify themselves with certificates, and messages can be signed or signed and encrypted.

MQTT (an OASIS standard) is a publish/subscribe transport built around a broker. A client publishes a payload to a topic such as plant/line3/press2/temperature; the broker forwards it to every client subscribed to a matching topic. Publishers and subscribers never connect to each other. MQTT defines three quality-of-service levels, retained messages (the broker keeps the last value of a topic for new subscribers) and a last-will message (published by the broker when a client drops off unexpectedly). It does not define what is inside the payload. That is left entirely to you.

Choosing by layer rather than by project

A choice that holds up in practice is to decide separately for each hop.

Controller to edge. If the PLC has an OPC UA server, use it. You get data types and names from the controller project instead of maintaining a hand-typed register map, and access can be restricted per node. For older controllers without one, the realistic options are the vendor's native driver or a fieldbus gateway, and the gateway then presents the data as OPC UA or publishes it to MQTT.

Edge to plant systems or cloud. MQTT fits when there are several consumers, when links are unreliable, or when the receiving side sits in another network zone. The device only needs an outbound connection to the broker, which is much easier to get through a firewall review than an inbound port on every machine.

A small, flat installation. With a handful of machines and a single SCADA or MES collector on the same network, adding a broker only adds a component to maintain. Direct OPC UA client/server is enough.

The two also overlap by design: the OPC UA specification includes a PubSub model that can use an MQTT broker as its transport, and the Sparkplug specification adds a fixed topic structure, payload format and device state handling on top of MQTT. Both exist because plain MQTT says nothing about meaning. Support for either varies by product, so check what your controllers and software actually implement before designing around them.

Faults you will meet on the OPC UA side

The client cannot connect although the network is fine. The most common cause is certificate trust. Each side must trust the other's application certificate, and on many servers a new client's certificate lands in a rejected list until someone moves it to the trusted list. Check this before chasing firewalls. Next most likely are a mismatch between the security policy the client requests and the ones the server allows, a host name in the endpoint URL that the client cannot resolve, and clock differences large enough to make a certificate look not yet valid or expired.

Short events are missing from the data. A subscription reports what the server saw at its sampling interval. A bit that goes on and off between two samples never appears. Requesting a faster interval helps only down to what the server supports; embedded servers often revise the request to a slower value, and the client is told the revised value. For pulses and counts, latch or count in the PLC and collect the latched value or the counter.

The server becomes slow or refuses new sessions. Embedded servers have limits on sessions, subscriptions and monitored items, and they share the CPU with the control program. Limits depend on the model and firmware, so read them from the manual. Several clients each subscribing to the same thousand tags is the usual way to hit them; one collector that redistributes the data is the fix.

Values look frozen. A deadband that is too wide, or a subscription that silently died after a network break and was not re-created by the client, both produce a flat line. Compare with a direct read of the node to tell them apart.

Faults you will meet on the MQTT side

Every consumer parses the data differently. Without an agreed topic hierarchy and payload schema, each publisher invents its own. Decide before the first device goes live: topic levels (site/area/line/machine/signal), payload format, units, and that the timestamp is taken at the source, not at the receiver.

Duplicate or missing records. QoS 0 can lose messages. QoS 1 guarantees delivery at least once, so duplicates are possible after a reconnect; make the consumer tolerant of them, for example by keying records on source timestamp and tag. QoS applies per hop, between a client and the broker, and delivery to a subscriber uses the lower of the published and subscribed levels. It also does not cover the time a publisher is offline unless the publishing device buffers locally.

A stopped machine still shows a good value. A retained message stays on the broker indefinitely. If a device dies, new subscribers still receive its last value as if it were current. Use the last-will message to publish an explicit offline state, and always carry a timestamp so stale data is recognisable.

Everything stops at once. The broker is a single point of failure by construction. Plan for it: local buffering at the edge, monitoring of the broker itself, and a redundancy option if the data matters.

Security and write access

Both protocols can be deployed safely and both are frequently deployed open. For OPC UA, do not leave the "None" security policy and anonymous access enabled in production. For MQTT, use TLS, per-client credentials and topic access rules on the broker; an unauthenticated broker lets any device on the network publish to any topic.

Treat write paths separately from read paths. Data collection needs read access only. If a higher-level system must send recipes or setpoints, restrict it to specific nodes or topics, and have the PLC validate ranges and machine state before accepting a value. Starting motion or changing safety-related parameters must remain under the machine's own control and safety functions, never under a remote data path.

A check order before you commit

  1. List consumers of the data. One collector points to OPC UA alone; several, or any in another zone, points to a broker upstream.
  2. Check what each controller offers natively and its documented session and item limits.
  3. Fix the naming: node structure in the PLC and topic hierarchy on the broker should map one to one.
  4. Decide where timestamps and buffering live. Both belong as close to the machine as possible.
  5. Test the failure cases on a bench: pull the network cable, restart the broker, restart the PLC, and confirm what the consumers see and how recovery happens without manual steps.

Step five is the one most often skipped, and it is where the difference between the two protocols shows up most clearly.
